Loyalty Engine

The Foundation the Agent Runs On
What's already built, building, or planned in the Flickpoint module

🏆
✓ Done
Reward Generation Engine
Daily transactional rewards (per invoice), monthly target-based rewards, and tier multipliers — all configurable by SKU, category, or product hierarchy. Dual ClickHouse + SQL ledger with full audit trail.
🎖
✓ Done
Tier Engine
Silver / Gold / Platinum tiers with 3 types of downgrade shields (Grace Period, Exhaustible, Cyclical). Creates real switching costs — outlets don't risk losing a hard-earned tier.
✅
⚙ Building
Approval + CN Conversion
Multi-stage approval gate before points hit wallet. Approved points auto-convert to Credit Notes (Points × Conversion Factor) and flow to DMS for invoice settlement. Loyalty has direct financial impact.
📱
✏ Scoped · Designing
GT Onboarding Flow
GT sales user registers outlet, completes KYC, and enrolls in campaigns from the field app. The agent's decisions surface here as actionable CTAs on the call prep screen.
📊
✓ Done
Retailer App
Outlet-facing app showing wallet balance, active campaigns, targets, live achievement, slab position, points in process, and CN tracking. The agent's campaign interventions surface here for outlet visibility.
⚙️
📋 Scoped
Admin Screens
Admin dashboard for rule builder, cohort config, tier setup, approval config, and reward master. Agent will call the underlying APIs directly; humans manage configuration here.
🗄
✓ Done
Dual Ledger Architecture
ClickHouse for daily reward entries and monthly summaries (OLAP, append-only). Azure SQL for financial wallet (immutable ledger). Agent queries ClickHouse to validate signals and measure outcomes.
Agent Layer — To Build

What Needs to Be Built for the Agent to Work
The loyalty engine handles calculation. The agent layer handles intelligence and action.

🔌
! Priority
Campaign Creation API
Campaigns are configured manually today. The agent needs to programmatically create rules, criteria, and slabs targeting a specific outlet cohort — fully via API. This is the single most critical capability for the agent.
👥
! Priority
Dynamic Cohort API
Agent needs to define target groups from computed logic — "lapsed outlets in Delhi, Gold tier, volume drop >20%" — and attach that cohort to a campaign. Cohort 2.0 architecture supports this; needs agent-callable exposure.
📡
! Required
MCP Surface (agent.run)
Following the FieldAssist vibe coding mandate — CLI + API + UI + MCP from day one. CPG-OS calls agent.run, agent.get_run, agent.describe over the normalized contract. Zero custom integration per orchestrator.
📈
! Required
ROI Modeling Layer
Agent shouldn't launch campaigns blind. Phase 1: industry benchmark lift rates. Phase 2: actual historical data from Flickpoint campaigns. The model self-improves as campaigns accumulate data.
🔁
! Required
Feedback Loop to CPG-OS
After intervention, agent monitors leakage metrics for 30/60/90 days and reports back: did churn stop? Volume recover? This closes the loop and makes the whole CPG-OS system smarter with each run.
📋
! Required
Agent Manifest + Read APIs
Agent publishes /.well-known/agent.json declaring capacity, actions, and SLOs. Read APIs expose loyalty state (outlet tier, balance, campaign progress) for validation and monitoring steps.
🗃️
! Standalone Mode
Company Data Read Layer
Standalone detection requires direct ClickHouse access across all business data — Sales orders, Visit records, SKU portfolio gaps, Distributor coverage, Scheme redemption. This is the agent's independent sense layer: it reads company data, surfaces the gap, then acts via loyalty. Without this, standalone mode cannot function.
